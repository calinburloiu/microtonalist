# Extract a `rig` module from `tuner`: design

- **Issue:** #363
- **Date:** 2026-10-15
- **Measured on:** `main` at `d1e49bdf`

## Goal

`tuner` holds two concerns: the tuning engine (tunings, the tuners of each protocol, tuning-change detection and the
tuning session) and the *rig*, the setup of tracks a performer plays, where each track is a per-instrument MIDI pipeline
that runs through the engine. Move the rig into a new `rig` module that depends on `tuner`, and name the types that
hold the whole setup of tracks after the rig, **without changing behaviour**.

Success means:

- `tuner` no longer contains any rig or track type;
- `rig` depends on `tuner`, and nothing in `tuner` depends on `rig`;
- the types of the [Naming](#naming) section carry their new names;
- every test still passes; both modules meet their coverage floors;
- the architecture docs describe the two modules.

## Why it is feasible today

The dependencies inside `tuner` already run one way. The track files use the engine's types; the engine files use no
track type, except for:

- `TunerModule`, which wires both halves (see [Composition roots](#composition-roots));
- six ScalaDoc links in `Tuner.scala`: four to `[[Track]]` and two to `[[TunerProcessor]]`.

No `private[tuner]` member is used across the boundary:

- `TrackManager.TrackThreadsNamePrefix` and `TrackThreadsGroup` are used only inside `TrackManager`.
- `Tuner.NoteHoldingPedals` is used only by the tuners.

Plugins are (de)serialized by `familyName` / `typeName`, never by class name, so tracks files and composition files are
unaffected by a change of package or of class name.

## Naming

A *rig* is the setup of tracks: the term names what a list of tracks is, as a whole. A `Track` and the types of one
track keep their names; the types that hold or handle the whole setup take the rig's:

| Today | Renamed to |
| ----- | ---------- |
| `TrackSpecs` | `RigSpec` (its file, `RigSpec.scala`, keeps `TrackSpec`) |
| `TrackSession`, `TrackService` | `RigSession`, `RigService` |
| `TrackManager` | `RigManager` |
| `TrackRepo`, with `readTracks`, `readTracksAsync`, `writeTracks`, `writeTracksAsync` | `RigRepo`, with `readRig`, `readRigAsync`, `writeRig`, `writeRigAsync` |
| `TrackRepoException`, `TracksNotFoundException`, `BadTracksRequestException`, `TracksReadFailureException` | `RigRepoException`, `RigNotFoundException`, `BadRigRequestException`, `RigReadFailureException` |
| `TrackEvent`, `TracksOpenedEvent`, `TracksClosedEvent`, `TracksReplacedEvent` | `RigEvent`, `RigOpenedEvent`, `RigClosedEvent`, `RigReplacedEvent` |
| `DefaultTrackRepo`, `FileTrackRepo`, `HttpTrackRepo`, `LibraryTrackRepo` (in `format`) | `DefaultRigRepo`, `FileRigRepo`, `HttpRigRepo`, `LibraryRigRepo` |

The new composition root is `RigModule`. A value or parameter named after a renamed type follows it (`trackSpecs` →
`rigSpec`, `trackSession` → `rigSession`, `fileTrackRepo` → `fileRigRepo`, `FormatModule.defaultTrackRepo` →
`defaultRigRepo`, …), and so do the test classes (`RigManagerTest`, `RigSessionTest`, `RigServiceTest`) and the prose
of the ScalaDocs ("track session" → "rig session").

These keep their names:

- `Track`, `TrackSpec`, `TrackIO` (`TrackInputSpec`, `TrackOutputSpec`), `TunerProcessor` and `TuningChangeProcessor`,
  which concern one track;
- the events of one track, `TrackAddedEvent`, `TrackUpdatedEvent`, `TrackMovedEvent` and `TrackRemovedEvent`, which
  now extend `RigEvent`;
- the members that name the tracks of the rig: `RigSpec.tracks`, `RigSession.tracks` and its `*Track*` methods,
  `RigService.replaceAllTracks`, `RigManager.tracks` and `replaceAllTracks`, `RigManager.TrackThreadsNamePrefix` and
  `TrackThreadsGroup`;
- every string literal of production code, so that no message or thread name changes;
- **the tracks file**: `TrackFormat`, `JsonTrackFormat`, `JsonTrackIOPluginFormat`, `InvalidTrackFormatException`,
  `FormatModule.trackFormat`, the JSON schemas under `json-schemas/v1/track/` and the `.mtlist.tracks` extension. A
  follow-up issue renames them after the rig; until then, `TrackFormat` carries a `// TODO #<n>` naming it.

The renames land **before the move**, in a commit of their own inside `tuner`, `format` and `app`. The move commit then
stays a pure move, and git detects the renamed files in both.

## Module boundary

| Stays in `tuner` | Moves to `rig` |
| ---------------- | -------------- |
| `Tuning`, `package.scala` (`DefaultCentsTolerance`) | `Track` |
| `Tuner`, `MtsTuner`, `MtsMessageGenerator` | `RigSpec` (`TrackSpec`, `RigSpec`) |
| `MonophonicPitchBendTuner` | `TrackIO` (`TrackInputSpec`, `TrackOutputSpec` and their plugins) |
| `MpeTuner` and its `Mpe*` helpers | `RigManager` |
| `TuningChange`, `TuningChanger`, `TuningChangeTriggers`, `PedalTuningChanger` | `RigSession`, `RigService`, `RigEvent` |
| `TuningSession`, `TuningService`, `TuningEvent` | `RigRepo` and its exceptions |
| `TunerModule` (shrunk) | `TunerProcessor`, `TuningChangeProcessor` |
| | `RigModule` (new) |

That is about 1,550 of `tuner`'s 6,040 lines of production code.

**The processors move to `rig`.** `TunerProcessor` and `TuningChangeProcessor` depend only on engine types, so either
module could hold them. They go to `rig` because they exist to make a tuner or a list of tuning changers a stage of a
track's `MidiSerialProcessor`, and `Track` is their only user. `TunerProcessor`'s attach and detach behaviour is part of
how tracks are wired.

**`RigRepo` moves to `rig`.** It is the port through which `RigSession` loads a `RigSpec`; its implementations stay in
`format`.

**`TuningSession` and `TuningService` stay in `tuner`.** `ui` and `app` use them without tracks, and
`TuningChangeProcessor` reaches them through `TuningService` from `rig`, the allowed direction.

## Package

The `rig` module's root package is `org.calinburloiu.music.microtonalist.rig`, which matches the module-to-package
table of `module-overview.md`.

- The moved files import the `tuner` types they use.
- `private[tuner]` in `RigManager` becomes `private[rig]`.
- The four `[[Track]]` and two `[[TunerProcessor]]` links in `Tuner.scala` become plain backticked names, since a
  module can't link to a module that depends on it.
- The ScalaDoc links from the moved files to `tuner` types are checked, and any that no longer resolve get a fully
  qualified name.

Keeping the `tuner` package in the new module (a split package) was rejected. It would save the import edits, but the
package would no longer tell which module a type lives in.

## Composition roots

Today `TunerModule(businessync, trackRepo, midiManager)` builds the tuning session and service, the track manager, the
track session and the track service, and its `close()` closes the track manager. It splits in two:

```scala
// tuner
class TunerModule(businessync: Businessync) {
  lazy val tuningService: TuningService = new TuningService(tuningSession, businessync)
  lazy val tuningSession: TuningSession = new TuningSession(businessync)
}

// rig
class RigModule(businessync: Businessync,
                rigRepo: RigRepo,
                midiManager: MidiManager,
                tuningService: TuningService) extends AutoCloseable {
  lazy val rigService: RigService = new RigService(rigSession, businessync)

  private lazy val rigManager = new RigManager(midiManager, tuningService)
  businessync.register(rigManager)

  private lazy val rigSession = new RigSession(rigManager, rigRepo, businessync)

  override def close(): Unit = rigManager.close()
}
```

`TunerModule` owns nothing to close any more, so it stops being `AutoCloseable`. `MicrotonalistApp` builds `RigModule`
from `tunerModule.tuningService` and closes `rigModule` instead of `tunerModule` on shutdown, still before
`midiManager`. As today, `RigManager` is registered on the bus when the module is built, so it receives the
`TuningEvent`s that `TuningSession` publishes.

This split is in scope here because the old `TunerModule` can't stay in `tuner`. The wider module wiring remains #100.

## Build graph

- **`rig`** (`lazy val rigModule`, id `rig`, artifact `microtonalist-rig`) depends on `tuner`, `businessync`, `common`
  and `sc-midi`, plus `commonTestUtilsModule % Test`. It declares `jsr305` like `tuner` does, since it uses
  `javax.annotation.concurrent`.
- **`format`** and **`app`** add `rigModule`. `format` holds `JsonTrackFormat`, `JsonTrackIOPluginFormat`, the
  `*RigRepo` implementations and `FormatModule.defaultRigRepo`.
- **`ui`** and **`composition`** don't change. They use only `Tuning`, `DefaultCentsTolerance`, `TuningService`,
  `TuningIndexUpdatedEvent` and `IndexTuningChange`.
- **`root`** aggregates `rigModule`.

No script under `bin/`, CI workflow or MCP server hard-codes the module list.

## Tests

The tests follow their subjects: `TrackTest`, `RigManagerTest`, `RigSessionTest`, `RigServiceTest`,
`TunerProcessorTest` and `TuningChangeProcessorTest` move to `rig`, and so do the two helpers that only they use,
`RecordingMidiReceiver` and `FakeMidiDeviceHandle`.

Tests on both sides use two helpers: `FakeTuner` and `TestTunings`. `rig` gets **trimmed copies** of them:

- a `FakeTuner` that keeps only `resetMessages`, `tuningMessages`, `processMessages` and `processedMessages`;
- a `TestTunings` that keeps only `justCMaj` and `justCRast`.

The full versions stay in `tuner`, whose `TunerTest` needs the rest: `canTune`, `untunableTunings*`,
`appliedTunings` and `previousTunings`. The fake's behaviour that matters to tracks, the restating of the tuning on
reset, lives in the `Tuner` trait, not in the fake, so the copies can't drift on it.

Two rejected alternatives:

- **A `tuner-test-utils` module.** It would have to depend on `tuner`, and `tuner`'s own tests would depend on it.
  sbt rejects that cycle even when one edge is `% Test` ("Cyclic reference involving …", checked with sbt 1.13.0
  on a throwaway build).
- **A `test->test` dependency, or a source directory shared by both test configurations.** The test conventions forbid
  `test->test`, which breaks scoverage. A shared directory would put one file in two build targets, which the
  per-target Metals symbol tools don't handle.

`RigModule` is a new file, so it gets a `RigModuleTest` to reach 80% on its own. It builds the module over a stub
`MidiManager` and a fake `RigRepo`, opens tracks through `rigService` and checks that `close()` closes them.

## Coverage

Splitting `tuner`'s current report by the boundary above gives:

| Module | Statements | Branches |
| ------ | ---------- | -------- |
| `tuner` after the split | 95.3% (1,801 / 1,890) | 94.1% (289 / 307) |
| `rig` | 87.8% (367 / 418) | 91.2% (52 / 57) |
| `tuner` today | 93.6% | 93.6% |

The figures leave out `TunerModule`, whose 8 statements are at 0% and split between the two modules. Both modules
therefore get `coverageSettings(stmt = 80, branch = 80)`.

If the measurement after the move falls under 80%, `rig` instead gets a floor 3% below the measured value and a
`// TODO #<n>` naming a follow-up issue to raise it, like the other modules in `build.sbt`. `RigModule` is held to 80%
either way.

## Implementation order

Each step leaves the build compiling and the suite green:

1. **Rename the rig types in place**, in `tuner`, `format` and `app`, after opening the follow-up issue for the tracks
   file. `git mv` the files whose type is renamed.
2. **Add the empty `rig` module:** `build.sbt`, its directories and `rig/CLAUDE.md`.
3. **Move the code.** Moving the rig breaks `format` and `app` until their imports change, so these changes land in
   one commit:
   - `git mv` the production files and their tests into `rig`, then change their package and imports;
   - add the trimmed test helpers;
   - split `TunerModule` and add `RigModule`;
   - rewire `MicrotonalistApp`;
   - update the imports and dependencies of `format`.

   Using `git mv` with small edits keeps git's rename detection, and so the history.
4. **Add `RigModuleTest`.**
5. **Rewrite the ScalaDoc links of `Tuner.scala`.**
6. **Update the docs.**
7. **Run the final checks** of `AGENTS.md`:
   - the tests of `tuner`, `rig`, `format` and `app`;
   - the coverage of `tuner` and `rig`, setting the floors as above;
   - the full suite;
   - `sbtn fixLint`.

## Out of scope

- Any behaviour change, including the open track issues listed above.
- Renaming the tracks file after the rig: its format types, JSON schemas and `.mtlist.tracks` extension (the
  follow-up issue).
- The wider rework of the module wiring (#100).
