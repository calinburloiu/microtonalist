# Extract a `track` module from `tuner`: design

- **Issue:** #363
- **Date:** 2026-10-15
- **Measured on:** `main` at `d1e49bdf`

## Goal

`tuner` holds two concerns: the tuning engine (tunings, the tuners of each protocol, tuning-change detection and the
tuning session) and the tracks, the per-instrument MIDI pipelines that run through it. Move the tracks into a new
`track` module that depends on `tuner`, **without changing behaviour**.

Success means:

- `tuner` no longer contains any track type;
- `track` depends on `tuner`, and nothing in `tuner` depends on `track`;
- every test still passes; both modules meet their coverage floors;
- the architecture docs describe the two modules.

## Why it is feasible today

The dependencies inside `tuner` already run one way. The track files use the engine's types; the engine files use no
track type, except for:

- `TunerModule`, which wires both halves (see [Composition roots](#composition-roots));
- six ScalaDoc links in `Tuner.scala`: four to `[[Track]]` and two to `[[TunerProcessor]]`.

No `private[tuner]` member is used across the boundary:

- `TrackManager.TrackThreadsNamePrefix` and `TrackThreadsGroup` are used only inside `TrackManager`.
- `Tuner.NoteHoldingPedals` is used only by the tuners.

Plugins are (de)serialized by `familyName` / `typeName`, never by class name, so tracks and composition files are
unaffected by a change of package.

## Module boundary

| Stays in `tuner` | Moves to `track` |
| ---------------- | ---------------- |
| `Tuning`, `package.scala` (`DefaultCentsTolerance`) | `Track` |
| `Tuner`, `MtsTuner`, `MtsMessageGenerator` | `TrackSpecs` (`TrackSpec`, `TrackSpecs`) |
| `MonophonicPitchBendTuner` | `TrackIO` (`TrackInputSpec`, `TrackOutputSpec` and their plugins) |
| `MpeTuner` and its `Mpe*` helpers | `TrackManager` |
| `TuningChange`, `TuningChanger`, `TuningChangeTriggers`, `PedalTuningChanger` | `TrackSession`, `TrackService`, `TrackEvent` |
| `TuningSession`, `TuningService`, `TuningEvent` | `TrackRepo` and its exceptions |
| `TunerModule` (shrunk) | `TunerProcessor`, `TuningChangeProcessor` |
| | `TrackModule` (new) |

That is about 1,550 of `tuner`'s 6,040 lines of production code.

**The processors move to `track`.** `TunerProcessor` and `TuningChangeProcessor` depend only on engine types, so either
module could hold them. They go to `track` because they exist to make a tuner or a list of tuning changers a stage of
a track's `MidiSerialProcessor`, and `Track` is their only user. `TunerProcessor`'s attach and detach behaviour is
part of how tracks are wired.

**`TrackRepo` moves to `track`.** It is the port through which `TrackSession` loads `TrackSpecs`; its implementations
stay in `format`.

**`TuningSession` and `TuningService` stay in `tuner`.** `ui` and `app` use them without tracks, and
`TuningChangeProcessor` reaches them through `TuningService` from `track`, the allowed direction.

## Package

The `track` module's root package is `org.calinburloiu.music.microtonalist.track`, which matches the module-to-package
table of `module-overview.md`.

- The moved files import the `tuner` types they use.
- `private[tuner]` in `TrackManager` becomes `private[track]`.
- The four `[[Track]]` and two `[[TunerProcessor]]` links in `Tuner.scala` become plain backticked names, since a
  module can't link to a module that depends on it.
- The ScalaDoc links from the moved files to `tuner` types are checked, and any that no longer resolve get a fully
  qualified name.

Keeping the `tuner` package in the new module (a split package) was rejected. It would save the import edits, but the
package would no longer tell which module a type lives in.

## Composition roots

Today `TunerModule(businessync, trackRepo, midiManager)` builds the tuning session and service, the track manager, the
track session and the track service, and its `close()` closes the track manager. It splits in two:

```scala
// tuner
class TunerModule(businessync: Businessync) {
  lazy val tuningService: TuningService = new TuningService(tuningSession, businessync)
  lazy val tuningSession: TuningSession = new TuningSession(businessync)
}

// track
class TrackModule(businessync: Businessync,
                  trackRepo: TrackRepo,
                  midiManager: MidiManager,
                  tuningService: TuningService) extends AutoCloseable {
  lazy val trackService: TrackService = new TrackService(trackSession, businessync)

  private lazy val trackManager = new TrackManager(midiManager, tuningService)
  businessync.register(trackManager)

  private lazy val trackSession = new TrackSession(trackManager, trackRepo, businessync)

  override def close(): Unit = trackManager.close()
}
```

`TunerModule` owns nothing to close any more, so it stops being `AutoCloseable`. `MicrotonalistApp` builds
`TrackModule` from `tunerModule.tuningService` and closes `trackModule` instead of `tunerModule` on shutdown, still
before `midiManager`. As today, `TrackManager` is registered on the bus when the module is built, so it receives the
`TuningEvent`s that `TuningSession` publishes.

This split is in scope here because the old `TunerModule` can't stay in `tuner`. The wider module wiring remains #100.

## Build graph

- **`track`** (`lazy val trackModule`, id `track`, artifact `microtonalist-track`) depends on `tuner`, `businessync`,
  `common` and `sc-midi`, plus `commonTestUtilsModule % Test`. It declares `jsr305` like `tuner` does, since it uses
  `javax.annotation.concurrent`.
- **`format`** and **`app`** add `trackModule`. `format` holds `JsonTrackFormat`, `JsonTrackIOPluginFormat`, the
  `*TrackRepo` implementations and `FormatModule.defaultTrackRepo`.
- **`ui`** and **`composition`** don't change. They use only `Tuning`, `DefaultCentsTolerance`, `TuningService`,
  `TuningIndexUpdatedEvent` and `IndexTuningChange`.
- **`root`** aggregates `trackModule`.

No script under `bin/`, CI workflow or MCP server hard-codes the module list.

## Tests

The tests follow their subjects: `TrackTest`, `TrackManagerTest`, `TrackSessionTest`, `TrackServiceTest`,
`TunerProcessorTest` and `TuningChangeProcessorTest` move to `track`, and so do the two helpers that only they use,
`RecordingMidiReceiver` and `FakeMidiDeviceHandle`.

Tests on both sides use two helpers: `FakeTuner` and `TestTunings`. `track` gets **trimmed copies** of them:

- a `FakeTuner` that keeps only `resetMessages`, `tuningMessages`, `processMessages` and `processedMessages`;
- a `TestTunings` that keeps only `justCMaj` and `justCRast`.

The full versions stay in `tuner`, whose `TunerTest` needs the rest: `canTune`, `untunableTunings*`,
`appliedTunings` and `previousTunings`. The fake's behaviour that matters to tracks, the restating of the tuning on
reset, lives in the `Tuner` trait, not in the fake, so the copies can't drift on it.

Two rejected alternatives:

- **A `tuner-test-utils` module.** It would have to depend on `tuner`, and `tuner`'s own tests would depend on it.
  sbt rejects that cycle even when one edge is `% Test` ("Cyclic reference involving …", checked with sbt 1.13.0
  on a throwaway build).
- **A `test->test` dependency, or a source directory shared by both test configurations.** The test conventions forbid
  `test->test`, which breaks scoverage. A shared directory would put one file in two build targets, which the
  per-target Metals symbol tools don't handle.

`TrackModule` is a new file, so it gets a `TrackModuleTest` to reach 80% on its own. It builds the module over a stub
`MidiManager` and a fake `TrackRepo`, opens tracks through `trackService` and checks that `close()` closes them.

## Coverage

Splitting `tuner`'s current report by the boundary above gives:

| Module | Statements | Branches |
| ------ | ---------- | -------- |
| `tuner` after the split | 95.3% (1,801 / 1,890) | 94.1% (289 / 307) |
| `track` | 87.8% (367 / 418) | 91.2% (52 / 57) |
| `tuner` today | 93.6% | 93.6% |

The figures leave out `TunerModule`, whose 8 statements are at 0% and split between the two modules. Both modules
therefore get `coverageSettings(stmt = 80, branch = 80)`.

If the measurement after the move falls under 80%, `track` instead gets a floor 3% below the measured value and a
`// TODO #<n>` naming a follow-up issue to raise it, like the other modules in `build.sbt`. `TrackModule` is held to
80% either way.

## Implementation order

Each step leaves the build compiling and the suite green:

1. **Add the empty `track` module:** `build.sbt`, its directories and `track/CLAUDE.md`.
2. **Move the code.** Moving `Track*` breaks `format` and `app` until their imports change, so these changes land
   in one commit:
   - `git mv` the production files and their tests into `track`, then change their package and imports;
   - add the trimmed test helpers;
   - split `TunerModule` and add `TrackModule`;
   - rewire `MicrotonalistApp`;
   - update the imports and dependencies of `format`.

   Using `git mv` with small edits keeps git's rename detection, and so the history.
3. **Add `TrackModuleTest`.**
4. **Rewrite the ScalaDoc links of `Tuner.scala`.**
5. **Update the docs.**
6. **Run the final checks** of `AGENTS.md`:
   - the tests of `tuner`, `track`, `format` and `app`;
   - the coverage of `tuner` and `track`, setting the floors as above;
   - the full suite;
   - `sbtn fixLint`.

## Out of scope

- Any behaviour change, including the open track issues listed above.
- The wider rework of the module wiring (#100).
