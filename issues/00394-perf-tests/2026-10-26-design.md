# End-to-end MIDI latency suite (#394): design

Date: 2026-10-26 · Based on commit `6d41684f` (`main`) · Branch `feature/perf-tests` · Status: draft, awaiting approval

Items marked **(my call)** were proposed by Claude and not discussed with the user; everything else was decided by the
user in the brainstorming conversation, or comes from issue #394 and the #383 design
(`issues/00383-arch-threading-and-ui/2026-10-20-design.md`).

## Intent

Microtonalist feels responsive when played, but nobody knows how responsive it is. The suite puts numbers on the
app's MIDI latency end to end and answers two questions:

1. **Baseline:** how good is the latency today, with its median and its worst cases?
2. **Verdict on #90:** do the threading and messaging changes of the #383 design (implemented by #90, in progress)
   make latency better or worse, and is the difference real or noise? The "before" build is `main` at `a8ba00df`.

After #90 the same suite becomes a regression tracker across versions: each run is committed, and the report shows how
each metric evolves and flags drift. Later, the `release` skill may run it and warn before a release; that is not part
of this change.

## Goals

- Infrastructure to write end-to-end latency test cases as Scala code, run them against the JAR of any commit, record
  the statistics of each metric in committed JSON files, and explore them in an HTML report.
- The test cases of issue #394 (see [Test cases](#test-cases-of-this-change)).

## Non-goals

- The project skill of issue #394 (build or find the JAR of a commit, set up the rig, run, compare two runs): postponed.
- The `release` skill's performance check.
- CI: the suite needs MIDI devices and depends on the machine, so it runs by hand.
- Machine probes for other operating systems than macOS (the design must allow adding them).
- Comparing runs across machines.
- Asserting the order of output messages, such as a note overtaking a tuning change (#385).

## Anti-goals

- Hard-coding macOS, the IAC Driver, a tuner or a device name in the infrastructure. IAC buses are only the setup the
  user has today; on Windows it would be another loopback driver.
- Committing raw samples.
- Making the normal test suite (`root/testOnly *`) or coverage launch the app or need MIDI devices.
- Changing the app to make it measurable: the suite treats the app as a black box, which is what lets it measure
  historic commits.

## Constraints

- Scala 3, sbt, the repo's conventions (brace syntax, TDD, ScalaDoc, lint, coverage).
- MIDI I/O through `sc-midi` / `sc-midi-javamidi`.
- JSON for both the suite's configuration and its results, with play-json. Not HOCON: the project will probably move
  from HOCON to JSON.
- The app runs in a separate process: `java -jar <jar> <composition> <app-config>`. That command line is the same at
  `a8ba00df` and today.
- Timestamps come from the suite's own clock (`System.nanoTime`) when it sends a message and when its receive callback
  runs, not from MIDI message timestamps. Durations are stored in nanoseconds.
- Tests never sleep (`docs/development/test-conventions.md`); they wait on what arrives, with timeouts.
- The report is a single page: HTML and JavaScript, no server logic, no build step.

## Design

### Module and invocation

**(my call)** A new module group `perf/` with one module `perf` (root package
`org.calinburloiu.music.microtonalist.perf`), depending on `sc-midi-javamidi` and play-json:

- `perf/perf/src/main/scala`: the infrastructure, unit-tested by TDD in `perf/perf/src/test/scala` like any module.
  These unit tests run in the normal suite and count toward coverage.
- `perf/perf/src/test/scala`: also holds the latency test cases. They are **canceled** (ScalaTest `assume`) when no
  JAR is given, so `root/testOnly *` stays green on any machine.
- `perf/results/`: the committed run files and their `index.json`.
- `perf/report/`: the report page.

`root` aggregates the module like any other, so compile, lint and coverage cover the infrastructure. A run passes its
parameters as ScalaTest config-map arguments, e.g.:

```bash
sbtn "perf/testOnly org.calinburloiu.music.microtonalist.perf.* -- -oNCXEHLOPQRMWS -Djar=/path/to/app.jar -Dcommit=a8ba00df"
```

`commit` is needed only for a JAR whose `BuildInfo` doesn't carry its commit (see
[Build identity](#build-identity)). Other parameters may override the configuration (e.g. the iteration counts).

### Configuration

A JSON file in the module's resources, `perf.json` **(my call: name)**, holds:

- **The two devices, required:** the one the suite sends on (the app's input) and the one it receives from (the app's
  output), each as `sc-midi`'s `MidiDeviceId` (`name`, `vendor`). The suite stops with a clear message when either is
  missing, or isn't available. The committed file holds them empty; the user fills them in.
  **(my call)** A local, git-ignored override file next to it may hold them instead, so the committed file needs no
  machine-specific names.
- **An optional machine name**, a friendly label for the report.
- **Defaults for a run:** the launch count, warm-up and timed iteration counts, the pace, timeouts.

The suite can pass a custom app config to the app, though no case needs one now. **(my call)** By default it still
passes a scratch config, so that the app never reads or rewrites the user's `~/.microtonalist/microtonalist.conf`.

### Test case model

A test case is Scala code in a test class. The user agreed on this shape (names and exact API are the builder's):

```scala
"MTS: pedal tuning change" in perfCase(
  tracks = "tracks/mts-pedal.mtlist.tracks",       // template; the devices' variables are filled in
  composition = "compositions/two-tunings.mtlist",
  ready = Ready.passThrough(NoteOn(0, 60, 64))
) {
  input("pedal")(ControlChange(0, 67, 127)) -> output("sysex")(MtsOctave1ByteSysEx(...))
  metric("pedal-to-sysex", from = "pedal", to = "sysex")
}
```

- **Given:** a composition from the test resources, and a **tracks template** from them, whose variables the suite
  replaces with the configured devices. The template picks the tuner and tuning changer; the infrastructure knows
  nothing about tuners.
- **Readiness:** each case defines when the launched app is ready, either by an output pattern to wait for after
  launch, or by a probe input sent until its expected output comes through. Tuners differ here: for example,
  `MtsOctave1ByteNonRealTimeTuner` sends nothing on reset. A case that isn't ready within its timeout fails.
- **When:** the case sends its input **series** in order. A series is a group of messages sent back to back, and it
  can carry a **mark**, a name.
- **Steps (my call):** an iteration is a sequence of steps. A step sends its input series back to back, then waits
  for all of its expected output series before the next step starts, so every step needs an output to wait for. The
  case with a held note is four steps: Note On, pedal, pedal back, Note Off. The pedal back comes before the Note Off
  because the Pitch Bend and MPE tuners send nothing on a tuning change while no note sounds.
- **Then:** the case expects its output series, which can be marked too. Matching rules:
  - Within a series, the messages must match in order. **(my call)** An expected message is either an exact message
    or a pattern (a Scala pattern match), such as a Note On of note 60 on any channel. The MPE tuner puts each new
    note on the member channel least recently used, so the channel changes from one iteration to the next. A pattern
    keeps the realistic 15-channel zone.
  - Across series, no order is imposed: each output series is matched on its own. A case keeps two outputs whose
    order may vary in separate series.
  - The output must meet the expectation. A missing, extra or different message fails the iteration, so that a mark
    can't land on the wrong series. The failure shows the expected and actual messages.
  - **(my call)** A failed iteration is a failed assertion. It fails its case at once: the suite stops that case's
    app and records the case as failed, and the run goes on with the next case.
- **Metrics:** a metric is a named pair of marks, from an input series to an output series. Its value for one
  iteration is the receive time of the `to` series minus the send time of the `from` series. **(my call)** The send
  time of a series is when its first message is sent; the receive time of a series is when its last message arrives.
- **State between iterations:** each iteration must leave the app as it found it, and its expected output must be the
  same every time, up to its patterns. The case writes that in, e.g. a Note Off after its Note On, or a second pedal
  back to the first tuning.
- **Formats across commits (my call):** each case has one set of resources for now, matching the formats of
  `a8ba00df` and today. When a format changes, the case picks its resources by the app's version. Examples are #365
  renaming the tracks file, or the app config moving to JSON. That choice isn't built until a format changes.

### A run

One run is one invocation of the suite, over the test cases it selects. For each case:

1. Render the tracks template with the devices, and write it with the composition and the app config into a scratch
   directory. The composition finds its tracks file next to it (`<composition>.tracks`).
2. Open the two devices.
3. **Launches.** **(my call)** Start the app several times, 3 by default, one after another, like JMH's forks: JIT
   decisions differ from one JVM to the next. For each launch:
   1. Start `java -jar` with the configured JDK (by default the suite's own), capture its output to a log file, and
      wait for readiness.
   2. **Warm-up:** run untimed iterations until the hot path has passed the JIT's top-tier compile threshold (around 10k
      calls). **(my call)** 10,000 iterations by default, back to back. This also warms up the suite's own receive path.
   3. **Timed iterations:** **(my call)** 1,000 by default.
      - Each iteration waits until its expected output has arrived, so iterations never overlap.
      - **(my call)** Its measured step, the one that sends a metric's `from` series, starts on a fixed **pace**, one
        every 50 ms by default, about a fast trill; its other steps start as soon as the previous one ends. Back-to-back
        steps would keep the app's threads busy, which hides the cost of waking an idle thread, part of the latency a
        player feels and likely to differ before and after #90. Pacing waits on a scheduler, not a sleep.
   4. Stop the app and wait for it to exit.
4. Compute the case's statistics and drop the raw samples.

Each launch's raw samples go into preallocated arrays. The suite's receive callback does nothing but timestamp and
store, and nothing logs on the measured path.

**(my call)** **Floor.** Before the first case, the suite measures its own floor with no app running: it sends on the
app's input bus and receives the same message back from it, which a loopback device like an IAC bus does. The run
records it as a metric of its own. It tells how much of every latency is the setup's own cost.

**(my call)** At the end, the suite prints a summary table (median, p99, max per metric) and writes the run file. A
failed case is recorded as failed, with its reason and no metrics; the other cases keep theirs.

With the defaults, the 6 cases below take about 17 minutes, mostly the paced iterations.

### Statistics

For each metric of a case, from the raw samples of all its launches:

- count, min, mean, standard deviation, median, p90, p95, p99 and max, computed exactly from the raw samples before
  they are dropped (**(my call)** nearest-rank percentiles);
- a **histogram** of the distribution. **(my call)** Its bins are log-spaced, each about 1% wider than the last, and
  only the non-empty ones are stored, as `[lower bound in ns, count]` pairs;
- **(my call)** each launch's own count, median, p99 and max, so the report can show when launches disagree.

### Results files

**(my call)** One file per run, `perf/results/<machine-id>/<UTC timestamp>-<app version>-<short commit>.json`, and
`perf/results/index.json`, which lists every run with what the report needs to pick one without opening every file:
its path, machine id and name, start time, app version and commit. The suite updates `index.json` after writing a run.

A run file holds:

- `schemaVersion`, and an open `extra` object for later additions;
- the start and end times (UTC, ISO-8601);
- **app:** version, commit and dirty flag, Scala version, the JAR's SHA-256 **(my call)**;
- **suite:** its own commit and dirty flag, because a change to the suite can move the numbers;
- **JVM:** vendor, version and the flags the app was launched with;
- **machine:**
  - its **id**. **(my call)** On macOS, the SHA-256 of the hardware UUID (`IOPlatformUUID`), so the committed file
    identifies the machine across runs without publishing the UUID itself.
  - the friendly name from the config;
  - model, CPU, physical and logical core counts, RAM;
  - OS name and version;
  - **(my call)** the power source and Low Power Mode, which change a laptop's CPU speed;
  - the two MIDI devices used.

  The machine probe sits behind an interface, with only macOS implemented. **(my call)** Audio devices aren't
  recorded: they aren't on the MIDI path.
- **config:** the launch, warm-up and timed iteration counts, and the pace;
- **cases:** for each, its name, tracks template and composition, its outcome, and its metrics with the statistics
  above.

### Build identity

The app's `BuildInfo` gains the commit and a dirty flag (`sbt-buildinfo` `BuildInfoKey.action` running git), so a JAR
built from now on describes itself. The suite reads `version`, `scalaVersion` and the commit from the JAR's
`BuildInfo`. For an older JAR, `a8ba00df` among them, the `commit` argument supplies the commit, and the dirty flag is
recorded as unknown.

### Report

A hand-written single page, `perf/report/index.html`, that reads `../results/index.json` and the run files with
`fetch`. All logic lives in the page. Browsers block `fetch` from a page opened from disk, so it is served by the JDK's
static file server:

```bash
"$JAVA_HOME/bin/jwebserver" -d "$(pwd)/perf"    # then open http://localhost:8000/report/
```

The same page could go on GitHub Pages unchanged. **(my call)** A charting library is allowed, loaded at a pinned
version, without a build step.

Layout **A, "Overview first"**, chosen by the user from the mockups:

- **Header:** a machine selector (by default the latest run's machine), a run selector (by default its latest run) and
  a "vs" selector (by default the previous run on the same machine). The report only ever compares runs of one machine.
- **Table:** one row per metric of the selected run: case and metric, median, p99, max, the change of the median
  against the "vs" run, and a drift flag (significant, not significant, new). A drifted row is highlighted. A failed
  case shows its reason.
- **Expanded row** (on click):
  - the metric's **timeline** across the machine's runs in time order, labeled by version and short commit, with the
    median and p99 by default and toggles for the other statistics;
  - the selected run's **distribution** on a log axis, with percentile markers, and the "vs" run drawn over it;
  - its statistics, the launches' spread, and the drift test's outcome;
  - the run's metadata: machine, JDK, Scala version, commits, config.

**Drift.** Latency distributions are long-tailed, so the test makes no assumption about their shape. **(my call)** The
page runs two tests on the histograms of the two runs:

- **Mann–Whitney U** for a shift of the whole distribution, each bin counting as a group of tied values;
- a **bootstrap confidence interval** for the change of p99, resampling from the histograms, because a tail can move
  while the median stays put.

A metric is flagged when a test is significant (p < 0.01, or a 99% interval that excludes zero) **and** the change
exceeds a minimum worth caring about, by default the larger of 5% and 20 µs. The thresholds are constants in the page.
Caveat: samples from one launch aren't fully independent, which makes the tests somewhat optimistic; the per-launch
statistics let a reader check that the launches agree.

**(my call)** The page's statistical functions are covered by a small test page, `perf/report/test.html`, that runs
assertions in the browser, since the repo has no JavaScript tooling.

## Test cases of this change

For each of the three tuners, `mtsOctave1ByteNonRealTime`, `monophonicPitchBend` and `mpe`, a track from the input
device to the output device with that tuner and a `pedal` tuning changer, over a composition with two tunings that
differ on the notes played. That makes 6 cases:

1. **Note pass-through:** from a Note On in to the Note On out (`noteOn→noteOn`). The case plays two notes whose
   offsets differ, one after the other, so that every Note On retunes: the Pitch Bend tuner sends a Pitch Bend only
   when its value changes, so a repeated note would measure a bare Note On.
2. **Pedal tuning change:** from the pedal's CC in to the tuning change out (`pedal→tuning`). With MTS the change is the
   SysEx. The Pitch Bend and MPE tuners send a tuning change only for a sounding note (`onTune` returns nothing
   otherwise), so their case holds a note through the pedal, and the change out is that note's Pitch Bend.

Each case reports, among the rest, the median, p99 and maximum the issue asks for.
