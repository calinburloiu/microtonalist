# End-to-end MIDI Latency Suite (#394) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

Date: 2026-10-26 · Based on commit `8c8a5138` (branch `feature/perf-tests`)

**Goal:** A `perf` module that measures the app's MIDI latency end to end against the JAR of any commit, records the
statistics of each metric in committed JSON files, and an HTML report to explore them; plus the 6 latency cases of #394.

**Architecture:** The suite launches the app as a black box (`java -jar <jar> <composition> <app-config>`), sends MIDI
on one device and timestamps what arrives on another with `System.nanoTime`. Infrastructure lives in
`perf/perf/src/main/scala`, unit-tested like any module; the latency cases and their ScalaTest glue live in
`perf/perf/src/test/scala` and are canceled when no JAR is given. A hand-written page under `perf/report/` reads the run
files under `perf/results/`.

**Tech Stack:** Scala 3.9 (brace syntax), sbt 1, ScalaTest 3 (`AnyWordSpec`), ScalaMock, play-json 3, `sc-midi` /
`sc-midi-javamidi` (CoreMIDI4J), sbt-buildinfo; vanilla JavaScript with Chart.js `4.4.1` from jsDelivr.

**Spec:** `issues/00394-perf-tests/2026-10-26-design.md` — read it before any task; this plan argues from it.

## Global Constraints

- Brace syntax, ScalaDoc on every public identifier, `// TODO #<issue>` only, no `return`, no `Thread.sleep` (also not in
  tests), Given/When/Then comments in tests, `AnyWordSpec` + `Matchers`. See `docs/development/*-conventions.md`.
- Strict TDD per task: failing test (compiling, failing for the right reason), then the minimal code, then refactor.
- MIDI I/O only through `sc-midi` / `sc-midi-javamidi`; JSON only with play-json (config and results; not HOCON).
- The app runs in a separate process: `java -jar <jar> <composition> <app-config>`; the suite never changes the app
  beyond `BuildInfo` (Task 1).
- Timestamps come from the suite's `System.nanoTime` when it sends a series' first message and when its receive
  callback runs; durations are stored in nanoseconds.
- Tests and the suite never sleep: they wait on what arrives, with timeouts; pacing waits on a scheduler.
- Anti-goals: no macOS, IAC, tuner or device name hard-coded in `src/main`; no raw samples committed;
  `root/testOnly *` and coverage never launch the app nor need MIDI devices.
- The measured path: raw samples in preallocated arrays, the receive callback only timestamps and stores, nothing logs.
- New module coverage: 80% statements and branches (`coverageSettings(stmt = 80, branch = 80)`).
- The report is one page of HTML and JavaScript, no server logic, no build step, served with
  `"$JAVA_HOME/bin/jwebserver" -d "$(pwd)/perf"`.
- Every new `.scala`, `.html` and `.js` file gets its license header from the pre-commit hook; don't add it by hand.
- Run tests only through `sbtn "<module>/testOnly <class> -- -oNCXEHLOPQRMWS"`; compile with the Metals MCP.

## Review Focus

1. **Leftovers of the previous launch:** the app's shutdown (Note Offs, resets) and its startup output (reset messages,
   the first tuning) must not fail the next launch's readiness or first warm-up iteration. Pinned by the CaseRunner test
   "discard the output an app sends while it starts" (Task 6).
2. **The app dies before it is ready** (bad composition, missing device: exit code 2): readiness must fail fast with the
   exit code and the log file, not wait out its timeout. Pinned by the CaseRunner test "fail at once when the app exits
   before it is ready" (Task 6).
3. **Device names with JSON-special characters** (`"`, `\`) in the tracks template must stay valid JSON. Pinned by the
   ScratchRig test "escape JSON-special characters in device names" (Task 7).
4. **A failed case in the middle of a run:** the other cases keep their metrics, the run file and `index.json` are still
   written and the summary shows the failure. Pinned by the PerfRun test "go on with the next case after a failed one"
   (Task 12) and the SummaryTable test "show a failed case's reason" (Task 11).
5. **Runs whose metrics differ** (a case added, renamed or failed in the "vs" run): the report shows "new" or the
   failure, never breaks. Pinned by the `stats.js` test "drift is new when the vs run lacks the metric" (Task 14) and the
   Playwright check of Task 15.

### Task 5: MIDI plumbing and pacing

**Files:**

  - `case class Received(message: MidiMsg, nanos: Long)`
  - `final class ReceiveBuffer(capacity: Int = ReceiveBuffer.DefaultCapacity) extends MidiReceiver` (`DefaultCapacity =

    when full; `def pollUntil(deadlineNanos: Long): Option[Received]`,

    both with `closeDevice`.

    `ScheduledExecutorService` releases a `Semaphore` at a fixed rate; `awaitNextTick` drains the permits, then
    acquires, so it always waits for the next tick.

case without an app", `RunResultJsonTest` "write the rig of a loopback case, which has none, as null".
