# #359 Documentation conventions — design

- Date: 2026-10-09
- Base: `main` at `a7caffb1`
- Issue: [#359](https://github.com/calinburloiu/microtonalist/issues/359), branch `doc/doc-conventions`

## Goal

Agents write documentation that is too verbose, and the architecture docs have drifted from an overview into a restating
of the code. Give agents conventions for every kind of doc, a skill for architecture docs with a size check enforced in
CI, and apply them to the docs that drifted most.

## Deliverables

1. `docs/development/doc-conventions.md`, always loaded.
2. The `architecture-docs` skill, with a size-check script and its tests.
3. A `docs` CI job running the script.
4. Trimmed `sc-midi/README.md`, `tuner/README.md` (plus a split-out `tuner/mpe-tuner.md`) and
   `midi-device-lifecycle.md`.
5. Trimmed comments in `MpeTuner.scala`, as a sample of the conventions.
6. One follow-up issue for the remaining architecture docs.
7. A draft PR resolving #359.

## 1. `doc-conventions.md`

Always loaded, so about 600–700 words.

- **Wiring.** `AGENTS.md` imports it in *Coding Conventions*. Its **Documentation** final check says to follow it and to
  invoke the `architecture-docs` skill when the change affects an architecture doc. `docs/development/README.md` and
  `CONTRIBUTING.md` list it with the other two conventions.
- **General rules.** Essentials only, as briefly as a human would write them. Don't restate the code. One home per fact;
  link instead of copying. Describe the current state: history lives in git, PRs and release notes. Cite issue numbers
  only for open work (a `TODO #n`, a subject-to-change note, a known limitation).
- **Kinds of docs.** A table of location and purpose for: ScalaDoc (contract of public identifiers), code comments
  (why, not what), architecture docs (orientation overview; see the skill), development guides (how-to for humans),
  agent docs (`AGENTS.md`, `docs/agents/`, skills: imperative, facts in context, rationale on demand), READMEs (what it
  is, how to start), papers and reference notes (`mpe-tuner-paper.md`, `mpe-spec.md`), release notes (the `release`
  skill).
- **ScalaDoc and comments.** Guidance, no ratio rule. A one-sentence summary first. Add only what a caller can't infer
  from the signature: units, failure behaviour, thread-safety, non-obvious constraints. No implementation walkthroughs
  in ScalaDoc. A comment gives a non-obvious *why* (ordering, invariant, workaround), never repeats the next line. A
  rationale that needs a paragraph belongs in the architecture doc or the paper; cite the section by name.
- **Papers.** Technical academic tone: precise definitions, claim then justification, no conversational asides. Length
  isn't capped, but the prose stays tight. Replaces the tone note in `tuner/README.md`.

## 2. The `architecture-docs` skill

Files: `.claude/skills/architecture-docs/SKILL.md`, `scripts/check_arch_doc_size.py` (Python 3, stdlib) and
`scripts/tests/test_check_arch_doc_size.py` (`unittest`). Written with `superpowers:writing-skills`, including its
red/green subagent runs (baseline without the skill, then with it, on prompts such as "document a new feature in
`format/README.md`" and "trim `format/README.md`"), in a scratch copy.

**Description:** use when writing, updating, splitting or reviewing a document under `docs/architecture/`, including
the Documentation step of a change that adds, removes or reshapes a module's key types or internal flows.

**Body, about 900 words:**

1. **Purpose.** Orient a human or an agent: the module's responsibility, its few most important types, and how things
   flow inside it and across its boundary. Details belong in ScalaDoc.
2. **What stays out.** Implementation details; exhaustive public API listings; `private` and `protected` members;
   mechanical dependency and dependent lists (`build.sbt` and `module-overview.md` have the graph; mention a dependency
   only where it matters to the picture); history. A `private[module]` type may appear, one line, when it is a main
   stage of an internal flow.
3. **Suggested shape** (not mandatory): Responsibility, Key types (grouped), Flows, Threading (when it matters), Subject
   to change.
4. **Mermaid diagrams.** `flowchart` for pipelines, `sequenceDiagram` for event and thread hand-offs, `stateDiagram-v2`
   for lifecycles. Small, and replacing prose rather than repeating it.
5. **Size budget.** Two pages of 500 words: 1000 words. OK up to 1200; warning (compacting recommended) at 1201–1500;
   error (compacting required) above 1500. Compact by rephrasing, removing details ScalaDoc owns, or splitting.
6. **Splitting.** When a doc is over budget and covers several capabilities. The split-out doc goes in
   `docs/architecture/<module>/<topic>.md`, has the same budget, and is linked only from its module README, where the
   parent keeps one summarising sentence and the link. `docs/architecture/README.md` lists, under *Other architecture
   material*, only docs that span modules and the papers.
7. **Maintenance checklist.** Every named type still exists (Metals `glob-search`); the flows are still true; remove
   what the change turned into a detail; run the size script; fix links into renamed anchors.
8. **Exemption marker.** `<!-- arch-doc-size: exempt (paper) -->`, only on papers and notes on external specs.
9. **The script is a black box.** Call it with `--help`; don't read its source.

**Script `check_arch_doc_size.py [--github] [PATH...]`:**

- With no path, checks every `docs/architecture/**/*.md` under the repo root.
- Counts the whitespace-separated words of the whole file, code blocks and diagrams included.
- A file with the marker in its first 10 lines is reported `SKIPPED`.
- Prints one line per doc: status, path, words, percentage of the budget. Each warning and error gets a one-line
  instruction ("compact recommended / required: rephrase, remove details or split; see the architecture-docs skill").
- Exit code 0 when all docs are OK or warned, 1 on any error, 2 on a usage error (e.g. a missing path).
- `--github` also prints `::warning file=…::` / `::error file=…::` annotations.
- Built test-first: thresholds at 1200/1201 and 1500/1501, marker inside and outside the first 10 lines, default
  discovery vs. explicit paths, exit codes, annotation format.

## 3. CI

A `docs` job in `.github/workflows/scala.yml`, with no JDK, running the script's unit tests and then the script with
`--github`. An error fails the build; a warning shows as an annotation. After this PR, only `format/README.md` (1283
words) warns.

## 4. Trimming

Each target about 1000 words and OK under the script. Facts an agent needs to orient stay; what ScalaDoc already owns
goes (the device-swap, lock-order and processor-hook details are all in ScalaDoc already).

- **`sc-midi/README.md`** (4983 words), no split. Responsibility (Scala MIDI API; Java Sound confined to `javamidi`;
  messages cross to Java Sound only in `JavaMidiDeviceHandle`; CoreMIDI4J on macOS). Key types in four groups, one or
  two lines each: devices (`MidiManager`, `MidiDeviceHandle`, `MidiEvent`, `JavaMidiManager`, `JavaMidiEnvironment`),
  messages (`MidiMsg`, `Midi1Msg`/`Midi2Msg`, `UnsupportedMidiMsg`, `JavaMidiConverters`), plumbing (`MidiReceiver`,
  `MidiTransmitter` and its three implementations, `MidiSplitter`, `MidiProcessor` with its attach/detach hooks,
  `MidiSerialProcessor`), helpers (`MidiChannelStateTracker`, `RpnSelector`/`RpnMessages`, `MidiNote`, `PitchClass`,
  `PitchBendSensitivity`). A mermaid flowchart of a message's path (input device → `asScala` → handle transmitter →
  processors → receiver → `asJava` → output device) and a short open/use/close list. Device states and events: one
  sentence linking `midi-device-lifecycle.md`. Threading: one paragraph (events published after the locks are released,
  on the publishing thread; lock order in `JavaMidiManager`). Subject to change: #306, #302, #292. Removed: method
  lists, reconciliation and swap mechanics, transmitter hook details, the tracker's Channel Mode rules, *Dependencies*,
  the #279–#307 history.
- **`tuner/README.md`** (3430 words), split. Keeps Responsibility; the Plugin pattern (one line); `Tuning`; the `Tuner`
  contract (`reset`/`tune`/`process`, `onReset`/`onTune`, `canTune` and clamping) in one paragraph; the protocols
  table; one sentence on `MpeTuner` linking `mpe-tuner.md`; tuning-change detection; track pipeline and tuning-change
  flow as mermaid flowcharts; device changes as a small diagram and 2–3 bullets; sessions, services and threading;
  subject to change, one line per TODO. Removed: the long `MpeTuner` reset paragraph (in `onReset`'s ScalaDoc), the
  allocator's file-by-file list, *Dependencies*.
- **`tuner/mpe-tuner.md`** (new, about 600 words). `MpeTuner`'s internal flow: a mermaid flowchart (classify channel →
  `route` → verdict → forward / relay RPN sequence / interpret → allocator → output); one line each for
  `MpeMessageRouting`, `MpeChannelAllocator`, `MpeExpression`, `MpeZone*` and the output RPN-selector record; which
  reconfigurations rebuild the allocators and which reset the receiver; links to the paper and `mpe-spec.md`.
- **`midi-device-lifecycle.md`** (1638 words, to about 900). Keeps the three-pair table, the "never say *connect*"
  rule, a short section per pair. Adds a mermaid `stateDiagram-v2` of `MidiDeviceHandle.State` over the available and
  open-requested axes. "How the three relate" becomes the attach/open rule, the four "a request isn't its effect"
  bullets and the two error cases merged. The #305 section shrinks to a few bullets; *Related documents* goes.
- **`docs/architecture/README.md`.** Drops the `tuner/mpe-spec.md` entry; keeps `midi-device-lifecycle.md` and
  `tuner/mpe-tuner-paper.md`.
- **Markers** on `mpe-tuner-paper.md` and `mpe-spec.md`.
- **Links.** The anchors between the three docs (`#device-handling`, `#device-changes`, `#subject-to-change-305`) keep
  their headings or get their links updated. `MidiProcessor`'s ScalaDoc cites `midi-device-lifecycle.md` by file only.

## 5. `MpeTuner.scala` comments

About 460 comment lines down to about 200–250; comments only.

- Keep, at one or two sentences each, the comments that guard against a regression: message ordering (dropped notes
  before setup messages; pedals before Pitch Bend), the unconditional Pitch Bend on a fresh allocation, the
  `stopNotesOn`/`rebuildAllocator` invariant, why `patchPbs` doesn't read the tracker.
- Replace spec derivations with a pointer to the paper section ("see the paper's *Zones* section").
- Drop or cut to one line the ScalaDoc of private methods whose name says it (`emitSlide`, `emitPressure`,
  `lowerZone`).
- Shorten `processMcm`, `applyPbsUpdate`, `emitZoneConfigurationResult`, `stopNotesOn` and
  `UnreachableExpressionPitchBendThreshold` to their contract plus one *why*; the public ScalaDoc (`onReset`,
  `canTune`, the class) to its contract.
