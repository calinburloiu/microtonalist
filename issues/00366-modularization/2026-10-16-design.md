# Modularization design

- **Date:** 2026-10-16
- **Based on commit:** `6de6d89d` (`doc/module-architecture-docs`)
- **Issue:** #366
- **Status:** approved design. It supersedes the draft proposal it was renamed from, whose history
  `git log --follow` keeps. [`outlook.md`](outlook.md) keeps the longer-term ideas it leaves out.

Packages abbreviate `org.calinburloiu.music.microtonalist` as `…`.

## Goals

- Keep the domain modules free of the MIDI engine, the format layer and the UI.
- Give each tuner, each tuning changer and each family of formats a module of its own.
- Prepare `sc-midi` for publishing as a standalone library.
- Recompile and retest less on each change.

This is a best-effort step: adding a tuner or tuning changer still touches the format module that lists its family's
plugins. The outlook's feature module groups and app-owned registration remove that.

## Context

Measured at `c8ada5c6`; the code at `6de6d89d` differs only by a ScalaDoc link.

- `composition` imports only `Tuning` and `DefaultCentsTolerance` from `tuner`, so the domain model compiles against
  the whole tuning engine (MPE, MTS, `businessync`, CoreMIDI4J). It also imports `PitchClass` and `MidiNote` from
  `sc-midi`, which `build.sbt` doesn't declare: they arrive through `tuner`.
- The whole engine shares the `TuningChange` ADT: the tuning changers return it, `TuningService.changeTuning` takes its
  effective cases, `rig`'s `TuningChangeProcessor` passes it from one to the other, and `ui` builds an
  `IndexTuningChange`.
- The `tuner` implementations don't reference each other: a tuner uses only the `Tuner` trait and `Tuning`, and the
  pedal changer only the `TuningChanger` trait, `TuningChange` and `TuningChangeTriggers` (98 lines):

  | Implementation | Main files | Main lines | Its format (lines) |
  | -------------- | ---------- | ---------- | ------------------ |
  | MTS | `MtsTuner`, `MtsMessageGenerator` | 282 | 91 |
  | Monophonic Pitch Bend | `MonophonicPitchBendTuner` | 357 | 57 |
  | MPE | the 7 `Mpe*` files | 2,529 (6,853 test) | 125 |
  | Pedal tuning changer | `PedalTuningChanger` | 158 | 76 |

- `format` has 52 files (4.4k lines, 3.8k test lines) and depends on `composition`, `rig` and `tuner`. Its imports
  fall into clean groups, which `FormatModule` wires. The one exception is `JsonPreprocessorHttpRefLoader`, an
  infrastructure file that throws the scales group's `ScaleNotFoundException` on a 404, where the file loader throws
  its own `JsonPreprocessorRefLoadException` for a missing file:

  | Group | Files | Depends on |
  | ----- | ----- | ---------- |
  | Infrastructure | `RepoSelector`, `DefaultRepoSelector`, `UriScheme`, `JsonPreprocessor` and its 2 ref loaders, `DeferrableRead`, `JsonPluginFormat`, `JsonConstraints` | `common` |
  | MIDI values | `JsonCommonMidiFormat`, `MidiNoteFormat`, `PitchClassFormat`, the package object (`uint7Format`, `ccNumberFormat`) | `sc-midi` |
  | Scales | `ScaleFormat`, `JsonScaleFormat`, `HuygensFokkerScalaScaleFormat`, `ScaleRepo` and its 4 implementations, `ScaleContextConverter`, `ScaleFormat{Context,Metadata,Registry}`, `JsonIntervalFormat`, `JsonIntonationStandardPluginFormat` | `intonation`, `businessync` |
  | Compositions | `Composition{Format,Repo,Repr}`, `{Default,File,Http}CompositionRepo`, `JsonCompositionFormat`, the mapper, reducer, reference and soft-chromatic plugin formats, `KeyboardMappingFormat` | `composition` |
  | Rigs | `RigFormat`, `JsonRigFormat`, `{Default,File,Http,Library}RigRepo`, `JsonTrackIOPluginFormat` | `rig` |
  | Tuners | `JsonTunerPluginFormat`, `Json{Mpe,MonophonicPitchBend,Mts}TunerPluginFormating` | `tuner` |
  | Tuning changers | `JsonTuningChangerPluginFormat`, which holds the pedal changer's format too | `tuner` |

- `JsonTunerPluginFormat` is an `object` with a hardcoded list of specs, and `JsonRigFormat` uses it and
  `JsonTuningChangerPluginFormat` as private implicits.
- Test helpers cross the future module boundaries. `format`'s tests use `JsonFormatTestUtils`, which needs only
  ScalaTest and Play JSON, and `FormatTestUtils`, whose three readers each serve the tests of one future module.
  `MtsTunerTest` uses `tuner`'s `TestTunings`, which `rig` already copies in trimmed form. `JsonRigFormatTest` reads
  real tuners and tuning changers, and `RigModuleIntegrationTest` uses `PedalTuningChanger`.
- `ui` uses three `tuner` symbols: `TuningService`, `IndexTuningChange` and `TuningIndexUpdatedEvent`.
- Outside `sc-midi`'s `javamidi` package (1.5k lines), `javax.sound` appears only in ScalaDoc links, and only `app` and
  `cli` import `javamidi`. Nothing enforces this: the JDK provides Java Sound to every module.
- What ties `sc-midi` to the rest of the repo:
  - Its only use of `common` is `Locking`, in 5 files (2 in the core, 3 in `javamidi`).
  - `MidiEvent extends BusinessyncEvent`, and `JavaMidiManager` takes a `Businessync` to publish its events.
    `BusinessyncEvent`'s only member, `name`, is unused, and `cli` builds a `Businessync` only to construct
    `JavaMidiManager`.
- `MidiNote.pitchClass` returns a `PitchClass`, so `PitchClass` can't leave `sc-midi`.

## Module conventions

Every module that a step creates or moves follows these rules.

**Build:**

- `lazy val <camelCaseId>Module = (project in file("<group>/<id>")).withId("<id>")`: the leaf folder is the ID.
- `name := "microtonalist-<id>"`, except `sc-midi-javamidi`, which follows `sc-midi`'s library naming.
  `intonation-format` takes the prefix: it depends on `format-core`, so it isn't part of the standalone `intonation`
  library.
- `commonSettings`; `disablePlugins(AssemblyPlugin)` except in `app` and `cli`; `commonTestUtilsModule % Test` when
  its tests need it. `root` aggregates it.
- A module declares every module it imports from, and never relies on a transitive dependency.
- Its coverage floor is 80/80 when it reaches it. Otherwise it's its measured coverage minus 3%, with the `TODO #<n>`
  of the module it came from, e.g. #179 for the `format` modules. A new module has no earlier floor to keep.

**Docs:**

- Every module but a test-utils module gets a `README.md`, a `CLAUDE.md` and a `docs/ARCHITECTURE.md`, as the
  `architecture-docs` skill describes. A split module's `ARCHITECTURE.md` splits with its code, and a topic doc moves
  with the code it describes.
- The module gets a row in the *Module index* of `docs/architecture/README.md`, and a place in the tree and the
  *Packages* table of `docs/architecture/module-overview.md`. For a package that several modules share, `…tuner` and
  `…format`, the table says which module holds what, since the Metals symbol tools need the owning module.
- `domain-concepts.md` groups the types by their new modules. `data-flow.md` changes only where a stage changes
  module.

**Tests:**

- Tests move with their code.
- A helper that the tests of several modules use goes to a test-utils module. Otherwise it goes to the tests of the
  module that uses it, trimmed if need be, as `rig`'s copy of `TestTunings` is.

## Steps

Each step ends with the final checks of `AGENTS.md`: module tests, coverage floors, the full suite, docs and
`sbtn fixLint`. Steps 1–5 move code without changing its behaviour, so the existing suite is their test; step 5's
fix of the HTTP ref loader and step 6, which changes an API, follow red/green. The *Depends on* columns list every
module that a module imports from, as found in the sources at `6de6d89d`.

### 1. Grouping folders

Every module moves into a grouping folder, which holds the modules of one area and nothing else: no `src`, no
`README.md`, `CLAUDE.md` or `docs/`. Only `root` stays at the repository root. A module's leaf folder name is its ID,
so the `.withId(<dir>)` convention and the scoverage inspector, which finds sources by `/<module_id>/src/`, keep
working. The final layout, with the modules that the later steps add:

```
app/     app/  cli/  config/  experiments/
base/    businessync/  common/  common-test-utils/
format/  format/  format-core/  format-test-utils/
midi/    sc-midi/  sc-midi-javamidi/
rig/     rig/  rig-format/
theory/  composition/  composition-format/  intonation/  intonation-format/
tuner/   tuner/  tuner-format/  tuning/  tuning-changer/  tuning-changer-format/
         tuner-mpb/  tuner-mpe/  tuner-mts/  tuning-changer-pedal/
ui/      ui/
```

- `app` holds the executables, and `config`, which only the `app` module uses. `base` holds the modules that know
  nothing about music.
- `theory` holds the music theory and its formats: intervals and scales, and how a composition maps them to tunings.
  `music` would fit every module of the repository, and `composition` would make the standalone `intonation` library
  look like a part of `composition`.
- `tuning` sits in `tuner`, the area of its package.

The step moves the 14 existing modules with `git mv`, without changing their code; each module's docs move with it.
It also:

- deletes the untracked build output (`target/`, `target-bsp/`) of the old module folders first, since `app/`,
  `format/`, `rig/`, `tuner/` and `ui/` become grouping folders;
- updates what names module paths: `build.sbt` and its convention comment, the JAR paths in `bin/mtlist` and
  `bin/mtlist-tool`, `bin/README.md`, `docs/architecture/README.md`, `AGENTS.md`, the root `README.md` and
  `docs/development/`;
- updates the relative links of the module docs, which gain a `../` into the root `docs/` and into the other modules;
- makes the size script's default find `<group>/<module>/docs/`, with a failing test first.

Done when:

- every relative Markdown link and `#heading` link resolves;
- the size script, given no path, finds the same 20 docs;
- the scoverage inspector reports a module in a grouping folder;
- `bin/mtlist` finds the JAR that `assembly` builds;
- no grouping folder has a `src/`.

### 2. `sc-midi-javamidi`

Move the `org.calinburloiu.music.scmidi.javamidi` package into a `sc-midi-javamidi` module that
depends on `sc-midi`, `common` and, until step 6, `businessync`. The CoreMIDI4J dependency and the
`CoreMidi4JEnvironment` coverage exclusion move with it, `app` and `cli` depend on it, and `sc-midi`'s
`ARCHITECTURE.md` splits. Java Sound use outside the module stays a review matter: the JDK provides it to every module.

Done when CoreMIDI4J is on the `Compile` classpath of `sc-midi-javamidi`, `app` and `cli` only.

### 3. `tuning`, `tuning-changer` and `tuning-changer-pedal`

Split the contracts of `tuner` into three modules, `tuner` and `tuning-changer` being siblings, and move the pedal
changer to a module of its own:

| Module | Package | Holds | Depends on |
| ------ | ------- | ----- | ---------- |
| `tuning` | `…tuner` | `Tuning`, `DefaultCentsTolerance`, the `TuningChange` ADT | `sc-midi` |
| `tuner` | `…tuner` | `Tuner`, `TuningSession`, `TuningService`, `TuningEvent`, `TunerModule`; the tuners until step 4 | `tuning`, `sc-midi`, `businessync`, `common` |
| `tuning-changer` | `…tuner.changer` | `TuningChanger`, `TuningChangeTriggers` | `tuning`, `sc-midi`, `common` |
| `tuning-changer-pedal` | `…tuner.changer.pedal` | `PedalTuningChanger` | `tuning-changer`, `tuning`, `sc-midi` |

- `composition` depends on `tuning` instead of `tuner`, and declares the `sc-midi` and `common` dependencies that it
  now gets through `tuner`. `rig` depends on `tuning`, `tuner` and `tuning-changer`, and on `tuning-changer-pedal` in
  `Test` scope. `ui` depends on `tuning` too, for `IndexTuningChange`. Until step 5, `format` depends on
  `tuning-changer-pedal`.
- `TuningChange` goes to `tuning` because both siblings need it. Leaving it in `tuning-changer` would take a
  `TuningService` method per effective change, which changes the service's API and `ui`'s call for little gain.
- `tuning` and `tuner` keep the `…tuner` package, so their imports don't change. `tuning-changer` gets a package of
  its own, so that the tuning changers have a namespace; `rig` and the format code change their `TuningChanger`
  imports.
- `PedalTuningChanger` moves straight to its final module, so that it moves once: it can't stay in `tuner`, which
  doesn't depend on `tuning-changer`.
- `tuner`'s `ARCHITECTURE.md` splits into the docs of the four modules above.
- Related open work: the `composition` refactor (#87) and scale lineage in tunings (#34), which would make `tuning`
  depend on `intonation`.

Done when `composition` depends on `tuning` and `sc-midi`, and not on `tuner`.

### 4. A module per tuner

Each tuner moves to a module of its own, in a subpackage of `…tuner`:

| Module | Package | Holds | Depends on |
| ------ | ------- | ----- | ---------- |
| `tuner-mpe` | `…tuner.mpe` | the 7 `Mpe*` files | `tuner`, `tuning`, `sc-midi` |
| `tuner-mts` | `…tuner.mts` | `MtsTuner`, `MtsMessageGenerator` | `tuner`, `tuning`, `sc-midi` |
| `tuner-mpb` | `…tuner.mpb` | `MonophonicPitchBendTuner` | `tuner`, `tuning`, `sc-midi` |

- Until step 5, `format` depends on them in `Compile` scope; after it, only `tuner-format` does, and `rig` and
  `rig-format` in `Test` scope. The same holds for `tuning-changer-pedal` with `tuning-changer-format`.
- `mpe-tuner.md` and the MPE Tuner paper move to `tuner-mpe/docs/`, and `MpeTuner`'s ScalaDoc link to the paper
  follows them.
- `tuner-mts` gets a trimmed copy of `TestTunings`, as `rig` has.
- **Scope.** Only tuners and tuning changers. The composition plugins (40–340 lines, no protocol or UI of their own)
  stay in `composition`, and the track I/O specs stay in `rig`.
- **Saved files are unaffected:** JSON identifies plugins by `typeName`, not by class name.

Done when `tuner` holds no tuner implementation.

### 5. Split `format`

A format module is named after the module whose types it formats, with `format` last as in its package, e.g.
`rig-format` in `…rig.format`. It sits in that module's grouping folder, a step toward the outlook's feature groups;
only `format-core`, the `format` aggregator and `format-test-utils` stay in the `format` folder.

| Module | Package | Holds | Depends on |
| ------ | ------- | ----- | ---------- |
| `format-core` | `…format` | the infrastructure and the MIDI value formats | `common`, `sc-midi` |
| `intonation-format` | `org.calinburloiu.music.intonation.format` | the scale formats and repos | `format-core`, `intonation`, `businessync` |
| `composition-format` | `…composition.format` | the composition formats and repos, with the composition plugin formats | `format-core`, `intonation-format`, `composition`, `intonation`, `tuning`, `sc-midi` |
| `rig-format` | `…rig.format` | the rig formats and repos, with the track I/O plugin formats | `format-core`, `rig`, `tuner`, `tuning-changer`, `sc-midi` |
| `tuner-format` | `…tuner.format` | `JsonTunerPluginFormat` and the tuner plugin formats | `format-core`, `tuner`, `tuner-mpe`, `tuner-mts`, `tuner-mpb`, `sc-midi` |
| `tuning-changer-format` | `…tuner.changer.format` | `JsonTuningChangerPluginFormat` and the tuning changer plugin formats | `format-core`, `tuning-changer`, `tuning-changer-pedal`, `sc-midi` |
| `format` | `…format` | `FormatModule`, which wires the modules above | all of the above, `rig`, `businessync` |

- Each plugin's format goes in a `format` subpackage of its plugin's package, e.g. `…tuner.mpe.format` for
  `MpeTuner`'s. `JsonTuningChangerPluginFormat` splits into the family format and the pedal changer's format.
- A rig file holds each track's tuner and tuning changer, so `JsonRigFormat` needs their formats. It takes a
  `Format[Tuner]` and a `Format[TuningChanger]` as constructor parameters, which `FormatModule` fills with the family
  formats of `tuner-format` and `tuning-changer-format`. `rig-format` then depends only on the plugin contracts,
  `tuner` and `tuning-changer`, and not on every plugin. Its tests depend on `tuner-format` and
  `tuning-changer-format` in `Test` scope.
- `JsonPreprocessorHttpRefLoader` throws `JsonPreprocessorRefLoadException` on a 404, as the file loader does for a
  missing file, so that `format-core` doesn't depend on `intonation-format`. A test reproduces the 404 first.
- Of the format modules, `app` depends only on `format`, until the outlook's app-owned registration replaces it.
- `intonation-format` depends on neither `composition`, `rig` nor `tuner`, so `experiments` can load scales without
  them.
- `JsonFormatTestUtils` moves to a new `format-test-utils` module, which the tests of every format module depend on,
  and each `FormatTestUtils` reader moves to the tests of the module it serves.
- `format`'s `ARCHITECTURE.md` splits into the docs of the modules above.

Done when:

- `rig-format` has no `Compile` dependency on a plugin module, `tuner-format` or `tuning-changer-format`;
- `format-core` has none on another format module;
- `intonation-format` has none on `composition`, `rig` or `tuner`;
- `app` depends on no format module but `format`.

### 6. Decouple `sc-midi` from `businessync`

- Replace the `Businessync` dependency with a SAM trait next to `MidiEvent`, e.g. `MidiEventPublisher` with a
  `publish(event: MidiEvent)` method, which `JavaMidiManager` takes. `app` passes a lambda calling
  `businessync.publish`, and a client that doesn't need the events, such as `cli`, passes a no-op instead of building
  a `Businessync`. A trait rather than a function type, so that its ScalaDoc can say on which thread the events come;
  a lambda still converts to it.
- `MidiEvent` stops extending `BusinessyncEvent`, so `Businessync.publish` accepts any `AnyRef`, as Guava's
  `EventBus.post` does. Wrapping `MidiEvent` instead would make `RigManager` subscribe to the wrapper.
- `businessync` stays unpublished: its API is incomplete and will change (#90).

Done when neither `sc-midi` nor `sc-midi-javamidi` depends on `businessync`, and `cli` doesn't either.

## Delivery

- **Prerequisite.** The move of the module docs into their modules (`doc/module-architecture-docs`) merges first:
  this design builds on its layout.
- **One sub-issue of #366 per step**, each with its own PR onto `main`, merged before the next step starts.
- **Order:** 1 → 2 → 3 → 4 → 5. Step 6 needs only step 2, since it changes `JavaMidiManager` in `sc-midi-javamidi`,
  so it can run alongside steps 3–5. Step 1 comes first so that each later step creates its modules in place, and
  step 5 after step 4 so that each plugin format moves to its final package once.
- **Plans, just in time.** Each step gets its own plan, `<date>-<sub-issue>-<topic>-plan.md` in this folder, written
  once the previous step has merged, against the code as it then is. Each step renames paths or packages that the
  next plan names, so a plan written earlier would go stale. This design fixes every final path and package, so no
  plan reopens them.

## Out of scope

- **Publishing `sc-midi`**, as two artifacts, `sc-midi` and `sc-midi-javamidi`. It gets an issue of its own, which
  takes over this open question: `sc-midi`'s only use of `common` is `Locking` (99 lines), which `config` and
  `format-core` use too. Should it be copied into `sc-midi` as package-private code, or extracted into a small
  published utility library? Until then `sc-midi` keeps its `common` dependency.
- **The outlook:** feature module groups, app-owned registration and the feature folder layout.
- **The small modules** (`ui`, `businessync`, `common`, `cli`): their boundaries are clear, and #99 and #90 will grow
  them.
- **The `FakeTuner` test doubles** in `tuner` and `rig`: an sbt test-scope cycle forces the duplication, and they
  differ.
